Feature Data Types

5.1.2. Feature Data Types#

Note

Data type refers to the way variables are represented and encoded in either numeric, categorical, date & time, boolean, or other less common formats.

Data features can be represented in many different forms. Some are obvious as with numbers and text, and some are more nuanced, as you’ll see with the differences between a numeric integer and a float. The way variables are represented and encoded in either numeric, categorical, date & time, boolean, or other less common formats, is known as the data type of a feature.

The associated data type with each variables is an extremely important topic. Not paying attention to this one will have consequences up and down your workflow. Functional processing and compilation errors are super common when you have mismatched types and are trying to perform certain operations on them.

You’ll see soon when we start to processing our data and they’ll need to be the correct data type. You can’t perform mathematical operations on text, and you don’t want to treat numeric variables as objects, so they must be cast into the correct type if they’re incorrect for some reason.

Let’s run through the most common feature data types with minimal examples below, and then we can jump into our real data. There are many others besides these main types, and even further subdivisions under each category type that you’ll learn as you begin practicing.

  • Numeric

  • Categorical

  • Date & Time

Numeric

As simple as it sounds - numeric features are numbers. There are a couple of different types and other common words you’ll hear to mean the same thing, so let’s see an example and go over them now.

Below we show a list of 5 integer, or whole numbers.

Note

Numeric, or continuous numbers, i.e. numbers that truly represent values on a numeric scale, will generally be expressed using an integer or float data type.

[1, 4, 0, 3, 1]

But don’t forget about everyone’s favorite grade school math topic, fractions! Besides whole numbers, you will run into fractional decimal numbers as well. Your analytical platform may refer to these by any number of terms, but likely you can expect to see them called float.

[5.57, -0.18, -0.94, 1.92, 2.46]

There are other edge cases with numbers for sure, but this is the main gist for numeric values. Continuous numbers, i.e. numbers that truly represent numbers on a numeric scale, will generally be expressed using an integer or float designation. The main point to keep in mind is that if something is a number, then certain rules must hold true.

For example, if you have three numbers, [3,6,9], then they must be able to be represented on a numeric scale at regular intervals and reference to each other such:

# 6 must be 2 times the value of 3
6/3

2.0

# 9 must be 3 times the value of 3
9/3

3.0

In this example of [3,6,9], 6 must be 2 times greater than 3, and 9 must be 3 times greater. Basic arithmetic.

Categorical

This is kind of a tricky one. There are several designations I could have used, but categorical seemed to make the most sense as the umbrella term. They may not all be “categorical” in the strictest sense, but categorical as a designation for the high-level classification of non-numeric values is appropriate.

Let’s create a couple of lists of categorical features to illustrate.

countries = ['Argentina', 'Belgium', 'Colombia', 'Denmark']

names = ['Mickey','Phil','Bob','Bill','Jerry']

colors = ['yellow', 'purple', 'green']

Pretty simple, right? Can you see why these would be called categorical features? Simple enough, because these values contained in the feature refer to some “category” or grouping, e.g. countries, names, colors.

Note

Categorical, or non-numerical features, i.e. values that are not represented or understood on a numeric scale, will generally be expressed using an object, string, or character data type.

The word categorical can be thought of as an over arching term to represent these types of variables, but it’s more likely you’ll see them referred to as an object, string, or possibly character in your analytical tool or platform. No matter the specific data type, they all essentially mean the same thing, non-numeric values represented as a “category” of some sort.

Before moving on, let’s address one of the exceptions relating to when categorical variables are represented as numbers. We’ll use a real example you may run across when dealing with personal demographic data. It’s not uncommon to see levels of education attained represented by the year, or grade of schooling, as below.

grade_level = [9,10,11,12]

Now ask yourself, even though these are truly “numbers”, are they really continuous numeric values? This is a tricky one, so think about it for a minute.

On the one hand yes, they can be continous numeric values if we think about them as years of schooling. Then they would map at regular intervals, meaning the distance between them maintains a linear and regular distance, and moving from year 2 to year 3 maintains the same interpretation as moving from year 11 to year 12. You’ve increased by 1 year.

On the other hand, and in the way the question was posed, the answer is no, however. The trick word being used here is education “level”. Thinking about education by levels instead of years. Does that carry the same interpretation? Hopefully you said no.

Think about it this way - Is moving from grade-level 9, to grade-level 10, understood by saying you attained a 10% higher education? Hopefully that doesn’t seem plausible to you. It really only makes sense if you think about it in terms of “year” and not “level”.

# Moving from grade 10 to grade 11 as a percentage change
(11 - 10) / 10

0.1

We’ll see this again, so don’t worry if it’s a little fuzzy. For now just think of the distinction as true numeric values are intended to be counted on a continous scale like money or sales, whereas as something like levels, groups, or indicators being represented using numbers are better encoded as categorical variables instead.

Date & Time

Next up, dates and time. This is an easy one to grasp, however the intricacies of actually dealing with them can often be maddening. We won’t complicate things until we need to, so for now we’ll just cover the basics.

Let’s type out a common date format in python below and check the data type.

begin_date = '05/12/2023 12:00:00'
print(type(begin_date))
print(begin_date)

<class 'str'>
05/12/2023 12:00:00

We can see what’s often going to happen when you run into date and time objects, regardless of the platform you’re using. If the format and syntax is not exactly what your application is expecting or isn’t explicted stated, it will default to a string or object data type of some sort like above. So in this case, we need to be explict and tell python that our date is actually a datetime data type.

from datetime import datetime

begin_date = datetime.strptime('05/12/2023 12:00:00', "%m/%d/%Y %H:%M:%S")
print(type(begin_date))
print(begin_date)

<class 'datetime.datetime'>
2023-05-12 12:00:00

Notice the difference in print outs by how the data was representation going into the type call. The first example came out exactly how it went in, as “05/12/2023 12:00:00”. The second example came out reformatted as a standard datetime object as “2023-05-12 12:00:00”, with a datetime data type.

The last thing we’ll introduce for now is that once you have dates and times represented as the correct data types, then you can perform all kinds of interesting operations with them. For a simple example, let’s create an end_date to go with our begin_date. The obvious operation might be that you want to know how many days have elapsed from the the beginning to end.

First we’ll create an ending date of 6/20/2023 at 4:00pm to go with our beginning date of 5/12/2023 at 12:00pm, and then check the difference by simply subtracting the two datetime objects.

# Create an end date as a "datetime" data type
end_date = datetime.strptime('06/20/2023 16:00:00', "%m/%d/%Y %H:%M:%S")

date_diff = end_date - begin_date
print(date_diff)

39 days, 4:00:00

Exactly as expected! The difference between the start and end date is 39 days and 4 hours.

There are actually several other data types we could cover, but for now this is plenty to get you working with enough understanding to cover the large marjority of what you’ll see with commom project types. Now that we have the details of data types out of the way, let’s move on to the main topic of the Data Quality Report - Feature Summaries.
